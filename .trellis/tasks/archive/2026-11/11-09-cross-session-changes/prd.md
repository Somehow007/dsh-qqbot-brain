# 跨会话鲜活性约定：CHANGES.md 广播位

## Goal

多会话并行开发同一项目时，让任意会话能实时感知其他会话的变动（定了方案 / 完成改动 / 定了方向 / 项目状态变化），保证每个会话开工时的认知是新鲜的——不同会话负责的模块/功能区域可能不同，但必须知道彼此动了什么。

## 背景与问题

现有留痕机制（task 归档 + journal + index.md 会话表）都是**会话结束才落笔**：

- `add_session.py` 在 finish-work 阶段才写 journal/index——并行会话 A 进行中时，会话 B 看不到 A 已经定了方案或改了代码；
- `get_context.py` 只给 git status / 近 5 条 commit / 任务列表，不含「别的会话最近干了什么」的语义层；
- 最关键的缺口：**没有任何约定要求会话开工时主动去扫一眼别人干了什么**。index.md 会话表客观上是个 changelog，但读侧无约定 = 形同虚设。

## Requirements

- **广播位**：新增 `.trellis/CHANGES.md`，追加式一行一条，四类事件落地即记：
  1. 定了优化方案/设计方向（plan/design 敲定，哪怕还没写代码）
  2. 完成一项改动/功能/部署
  3. 定了后续发展方向（roadmap、下一步决策）
  4. 项目状态/结论性认知变化（评估结论、线上状态、阶段判断）
- 条目格式：`- YYYY-MM-DD HH:MM | 事件一句话 | → 指针（task 目录 / journal session 号 / commit）`；只写索引不写细节，细节永远以 task prd/journal 为准。
- **读侧硬约定**：每个会话开工（接到第一个实际需求）前先 `tail -30 .trellis/CHANGES.md`，扫到自己不掌握的条目就顺指针读对应档案，再动手。
- 有界：文件只留最近 ~100 条，超出删旧（细节不丢，在 task/journal/index.md）。
- 不替代现有机制：「问题存档」「归档两层流程」「journal」照旧，CHANGES.md 只是广播位/目录。
- 同 checkout 并行会话文件即时可见；条目随正常提交走，跨分支合并后也有痕。

## Acceptance Criteria

- [x] `.trellis/CHANGES.md` 存在，有格式说明头 + 种子条目（最近几次 session 回填）
- [x] AGENTS.md「项目约定」新增硬约定条款（写侧四类触发 + 读侧 tail 扫描）
- [x] MAP.md 同步新入口（意图表 + 档案层表）
- [x] 本任务自身成为 CHANGES.md 的第一条实战条目（dogfood）

## Resolution（2026-11-09）

### 遇到了什么问题

用户担心多会话并行写项目时互不知晓彼此变动。排查确认缺口真实存在：现有留痕（task 归档、journal、index.md 会话表）全在**会话结束才落笔**，`get_context.py` 只给 git/commit/任务列表，且**没有任何约定要求会话开工时主动扫别人干了什么**——写侧有档案、读侧无约定。

### 怎么解决的

新增 `.trellis/CHANGES.md` 追加式广播位：四类事件（定方案/完成改动/定方向/状态结论变化）落地即记一行 + 指针；AGENTS.md 项目约定新增「跨会话广播位」硬约定，写侧四类触发、读侧开工 `tail -30` 扫描；MAP.md 意图表/档案层表/命令速查三处同步。本文件带 8 条回填种子条目，本任务自身为第一条实战条目。

### 后续优化方向

- 若条目长期没人写/没人读（约定空转），考虑把 `tail` 输出并入 `get_context.py` 或 Devin SessionStart hook 强制注入；
- 并行写冲突、条目超 100 条的压缩策略、跨 worktree 传播效果——实盘观察后再调；
- 若四类触发太粗/太细，按实际遗漏案例修订触发清单。

### 什么时候干的

2026-11-09 单会话完成：建任务 → 写 prd → 建 CHANGES.md → 改 AGENTS.md/MAP.md → commit `7d298c0` → 归档。

### Key Decisions

- **不复用 index.md 会话表当广播位**：它只在会话结束由 add_session.py 写，覆盖不了「进行中」这个最关键的窗口；且一行一个 session 粒度太粗，不含「定了方案」这类事件级信号。
- **放 .trellis/ 根而非 workspace/**：广播位是跨开发者的项目级状态，不属于某个 dev 的 journal。
- **只写索引不写细节**：防腐烂——细节单点在 task prd/journal，广播位失效了也只是目录失效，不丢信息。

### 验证结论

- 文件已建、约定已入 AGENTS.md（always-on，所有平台会话可见）、MAP 三处已同步；
- 提交 `7d298c0` 顺带带上了两个前序会话遗留 staged 未提交的归档任务目录（11-08-framework-vs-selfbuild、11-08-resume-kit）——本就是该入库的档案，无害但需注意并行会话的 staging 区是共享的。

## 补记（2026-11-09，归档后用户追问）

**问**：几天前、几次更新前的旧会话被恢复时，也能感知变动吗？

**答 + 补丁**：机制上天然支持——条目带时间戳，旧会话往回读到早于自己最后活跃时点为止即可增量补课，天数/更新次数不设限。但原措辞「接到第一个实际需求」对被恢复的旧会话不成立（它的首个需求在过去），故把「开工」定义扩为三种触发：新会话首个需求、旧会话被恢复继续、同会话跨时段开新任务。CHANGES.md 头部补增量读法说明；另注意 always-on rules 每轮都在上下文里，规则文本本身对旧会话也是新鲜的，不受会话年龄影响。
