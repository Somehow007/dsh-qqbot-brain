# 迭代节奏讨论：串行小步上线 vs 攒批

## 问题存档

- **时间**：2026-11-11（跨零点会话，承接 11-09~11-10 迭代 A/B 工作）
- **用户提问**：迭代是一次都做好，还是没做完一个，跑两天看一下再评估、修好后再开下一个迭代？
- **前置档案**：`tasks/11-09-iteration-upgrade-plan/iteration-plan.md`（七迭代路线图 A-G）、`archive/2026-11/11-09-iteration-a-three-track`、`archive/2026-11/11-09-iteration-b-ye-shunguang`、`tasks/11-10-consolidate-track-gaps`（B 走查遗留 F1-F4）

## 背景事实

- 迭代 A（11-09 上线）：部署当日走查即发现多处问题并完成补修（self 三态透传、情绪盖章口径、modalPersonaId、strength 地板、noteChar 回落），随后归档。
- 迭代 B（11-10 上线）：叶瞬光接入+per-persona MOODS；流萤人设包走查又发现 F1-F4（语义巩固不继承 self 轨 / manual 会话 modal 单视角 / import 不补向量 / 人设包缺 AI 身份条款），其中 F1 有生产时效（种子次日即触发巩固窗口），已立 `11-10-consolidate-track-gaps`（P1）。
- 即项目实际已在跑「单迭代上线→走查→修好→下一个」循环，且每轮都抓到真问题。

## 结论：维持串行小步，不攒批

**不建议把 A-G 一次做完再上线**，理由：

1. **归因困难**：A-G 全部落在检索/注入/蒸馏/存储同一链路上，叠着上线后任何异常（串味、噪声、成本突增）无法定位是哪一层引入。
2. **生产数据风险叠加**：A 已做过 attitude 归并这类生产数据改写；未验证稳定前再叠 D 的 schema/op 改动，回滚面成倍放大。
3. **成本一线失效**：约定要求每迭代成本增量可测、可建模；攒批后单迭代成本 delta 不可分。
4. **观察基线污染**：B 的观察窗需要干净的注入行为；C 的 recall 门控一旦上线就改变注入内容，会污染 B 的自测信号。
5. **方案本身已定此纪律**：iteration-plan §0「小步上线」+ E 项「不排期不预做，按信号取用」。

## 关键修正：「跑两天」不是固定时长，是信号驱动

观察窗 = 收集到该迭代验收/走查信号为止，不是死板 48h。按迭代性质分档：

| 迭代类型 | 观察窗形态 | 依据 |
| --- | --- | --- |
| 机制/schema 类（A、C、D） | 本地测试+eval+云端走查为主，墙钟观察价值低 | 行为确定性强，单测/eval 可覆盖；除非涉及时效迁移（A 的归并即反例） |
| 体验/人格类（B） | 用户自测=观察本身，至少跨天 | 记忆系统 day-scale 定时器（minAgeDays=1、衰减、巩固、画像漂移）决定了当日走查看不到次日行为——F1 正是「种子次日触发巩固」才暴露的 |
| E 储备项 | 信号驱动，不看日历 | 触发信号未出现就不动工 |

**部署串行、开发可流水线**：C/D 与 B 的观察结果互不阻塞（计划 §10 决策点 2），若 companion（F）近期要动工，可并行本地开发 C/D；但部署仍等 B 观察窗关闭+F1-F4 修完——F1 未修时 C 的深召回可能放大已污染的跨轨记忆，顺序上 F1-F4 应先于 C 部署。

## 落地的工作节奏（建议）

```
做迭代 N（本地验证）→ 备份部署 → 云端走查 → 观察窗（信号驱动）
  → 窗口内发现的问题进修复队列（先修，不开 N+1 部署）
  → 信号收齐/问题清零 → 归档 N → 开 N+1
```

- 窗口内可并行：下一迭代的本地开发、eval fixture 准备、人设包维护（不动生产注入面）。
- 「修好」的判据 = 走查清单全过 + 遗留问题归零或明确降级记录，不是「过了两天」。

## Key Decisions

- 迭代节奏：**串行小步上线**，观察窗信号驱动（非固定天数），开发可流水线但部署严格串行。
- F1-F4（`11-10-consolidate-track-gaps`）应先于迭代 C 部署完成——C 的召回能力会放大现有跨轨污染。
