# AI 驱动开发工作范式总结

## 问题存档

- **时间**：2026-11-11（跨零点会话，承接迭代 A/B 工作与 iteration-cadence 讨论）
- **用户提问**：当前用 Devin/AI 开发工具写项目的方式有啥问题？和行业专人（大小公司开发人员）还有哪些差距？是否要总结一套工作范式？
- **前置档案**：`tasks/11-11-iteration-cadence`（迭代节奏）、`tasks/11-09-iteration-upgrade-plan`、`tasks/11-10-consolidate-track-gaps`（F1-F4）

## 讨论结论

**方式本身没有根本问题**——已在实践的纪律（Trellis 上下文管理、可执行走查、成本一线、串行小步上线、全量档案）已是相当成熟的 AI-native 工作流，超过只用 AI 当补全工具的开发者。真正的薄弱点三个：

1. **理解债（comprehension debt）**：AI 产出快、人吸收慢。F1-F4 即典型病灶——迭代 A 加 `self` 轨，语义巩固消费路径漏传导，「局部正确、全局不一致」。对策：机制变更强制做消费点审计；关键机制定期让 AI 考自己。
2. **自审自写同源盲区**：写代码的 AI 与走查的 AI 共享盲区，「看起来对」恰是 LLM 审查最易漏处。缓解已有（可执行 curl/快照 diff/真实流量信号），补 fresh-eyes 交叉评审。
3. **工程卫生小项**：API token 走 URL query（进 shell history/代理日志）；群消息进 LLM prompt 的注入/记忆投毒面未评估；开发侧 token 成本无账（运行时成本核算很细，工作法成本没有）。

**与行业专人的差距**（诚实版）：产出纪律已接近中级专人；差距集中在——

- 第一手理解深度（面试深挖/疑难排查时可能跟不上）；
- 团队尺度经验（被人 review、CI 门禁、on-call、跨人 API 契约——单人项目无样本）；
- 长时维护（依赖升级/CVE 响应、breaking change——项目两月余无样本）。

补法不是加工具，是刻意练习。另提醒：项目为 TS/Node，若目标 Java 岗，简历证据链是「工程质量与系统设计」而非「Java 技能」，JVM/并发/Spring 需另备。
