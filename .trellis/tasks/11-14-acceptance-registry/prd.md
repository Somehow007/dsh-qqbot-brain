# 验收登记处机制

## 问题（2026-11-14 用户提出）

线上数据集积累慢，单次走查样本不足以反映真实质量——但现行做法是「走查一次→写 Resolution→归档」，观察项只留在 prd 散文里，任务一归档就失去跟踪载体；且「已部署/已走查」容易被误读为「已验收」。需要一个机制：

1. 记住各阶段需要复查、走查的地方；
2. 数据集不足时只记录情况不闭环，后续可再走查；
3. 彻底没问题、数据集能反映质量时才能验收结束；
4. 把各迭代的走查/验收点整理成规范或文档。

## 分析：验收其实是三级，不是一档

| 级 | 内容 | 关闭条件 | 载体 |
|---|---|---|---|
| L1 代码验证 | typecheck/test/build/eval | 提交即过，二元 | CI/本地命令 |
| L2 部署验证 | 服务起、特性 on、端点通 | 部署时冒烟 | brain.log/HTTP |
| L3 生产实证 | 行为在真实数据下符合预期 | **证据达阈值**（N 样本或特定事件），可能跨多次走查、跨任务存活 | 本登记处 |

现行流程把 L3 混在 L1/L2 里一次走查了事——这就是「样本薄也归档」的根源。归档语义应为「工作完成」，验收状态独立存活。

## 决策

**方案：验收登记处 `.trellis/acceptance.md` + prd 验收分层 + 归档前提改写**（用户确认方向后实施，纯文档/流程零代码）

- **登记处**（`.trellis/acceptance.md`）：实证项唯一台账。每项含 ID/来源/验证方法（可执行）/证据阈值/触发类型（事件·样本·抽查）/状态机（待触发→观察中→已通过/打回）。持续观察项单列不闭环。
- **prd 验收分层**：任务「验收标准」分代码验收（随提交关）与实证验收（部署时登记台账）；走查协议约定单次只记情况、达阈值才通过。
- **归档前提**：实证项已登记 ≠ 已通过；台账项可跨任务、跨迭代存活直到达标或显式放弃。
- **AI-WORKFLOW 衔接**：新纪律先进「待补纪律 backlog」立条，跑通若干次走查后再沉淀进 `.trellis/spec/`（遵循 AGENTS.md 既定纪律养成路径）。

### 证据阈值类型（设计要点）

- **样本型**：需 N 次同类事件（如搜索回合 ≥10）——时间驱动，定期走查累计；
- **事件型**：需特定场景出现（如多角色混合巩固批、真实召回提问、AI 身份提问）——可能长期不触发，标「待触发」不算失败；
- **抽查型**：持续质量观察（画像泛指、说教化、向量覆盖）——不闭环，每次走查顺手记。
